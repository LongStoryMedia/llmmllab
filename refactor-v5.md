# Comprehensive Requirements Document: Refactoring Agentic System to LangGraph-Based Architecture

## Executive Summary
This master requirements document merges all unique content from three historical versions (v3 preferred, then v2, then v1) with no omissions or duplicates. It defines a fully LangGraph-compatible, composable agent architecture, incorporating advanced streaming, intent-driven workflows, dynamic tool management, adaptive RAG, robust state/course error handling, and rigorous validation/testing for production. The Composer service is the authoritative orchestrator and runtime, delivering both real-time streaming and resilient batch workflows, validated on LangGraph V1-alpha best practices.

## 1. Current State Analysis
### 1.1 Architecture Problems Identified
- Manual, fragmented orchestration across server components such as title generation, summarization, and memory retrieval[3].
- Dynamic tool logic embedded in the server: no composability, modularity, or registry[2][3].
- Tight pipeline coupling: direct factory pattern inhibits flexibility[3].
- Mixed approaches to state and resource management, including inconsistent checkpointing and lifecycle management[1][3].
- Streaming handled only for primary agent, with secondary agents/tools lacking streaming support[2].
- Circuit-breaker and error handling scattered, risking reliability.

### 1.2 Current Component Responsibilities
- **Server**: HTTP, legacy orchestration, config, and profiles[3].
- **Composer**: Graph construction, orchestration, registry, workflow cache, intent analysis, state manager.
- **Runner**: Pipeline execution (stream/run/embed), resource management.
- **Tools**: Static (search, summarization) and dynamic (generated by LLM, currently ad-hoc).

### 2.2 Architectural Shift Validation (LangGraph V1-alpha)
- All complex graph execution is centralized in the Composer service, which leverages **Durable Execution**—state persistence and recovery in case of client disconnects.[2]
- Composer hosts all state, node, and graph logic. Client interacts via a single async streaming endpoint (WebSocket/SSE), receiving event envelopes.
- Composer's modular structure includes agents, tool orchestrators, specialized RAG nodes, and multi-agent routing logic.

## 3. Detailed Functional Requirements

### 3.1 Unified GraphState Schema

All nodes communicate through a Pydantic GraphState model, enforcing authoritative context.
Mandatory fields—each with reducer:

| Field Name            | Type         | Reducer      | Purpose                                                |
|-----------------------|--------------|--------------|--------------------------------------------------------|
| messages              | List         | x.concat(y)  | Conversation history/final outputs/token streaming     |
| intent_classification | IntentSchema | y            | Output from LLM Intent Agent, drives workflow selection|
| required_tools        | List         | y            | All tools collected/generated for this run             |
| search_results        | str          | y            | Consolidated RAG synthesis output                      |
| rag_depth_config      | str          | y            | SHALLOW/DEEP; Flow driver for RAG routing              |
| progress_updates      | List         | x.concat(y)  | Granular progress signals; tool/crawl steps            |

(Full context model implemented in composer/state.py)[2][3]

## 4. Streaming Architecture (Selective Modes)
- **Primary Chat Generator Node**: Streams LLM tokens via LangGraph's `messages` mode—real-time updates, progressive display, low latency.[2][3]
- **Upstream/Supporting Nodes** (Intent Classification Agent, Tool Agent, RAG Executor): Use `updates` and `custom` streaming modes for state deltas and transparent operational feedback. E.g. display "Tool registry accessed" or "Fetched 100/100 records".[2][3]
- Streaming payload is serialized with type discriminator (`token_chunk`, `state_update`, `progress_signal`). Transport via WebSockets/SSE. Client parses envelope to route data to UI or workflow progress[2].

### 4.1 Node Definitions and Streaming Config
| Node Type           | Function                              | Required Streaming Mode | Data Payload       | User Experience           |
|---------------------|---------------------------------------|------------------------|--------------------|---------------------------|
| Chat Generator      | Final LLM/conversational response     | messages               | tokens+metadata    | Real-time display         |
| Intent Agent        | Intent classification/policy output   | updates                | state deltas       | "Analyzing intent..."     |
| Dynamic Tool Agent  | Tool discovery/generation/composition | updates/custom         | progress signals   | "Accessing registry..."   |
| Deep RAG Executor   | Web crawl/synthesis                   | updates/custom         | custom progress    | "Fetched records..."      |

## 5. Configurable Knowledge Retrieval — Adaptive RAG
- **Intent-driven RAG config**: Upstream LLM-based agent (IntentClassifier) sets `ragdepthconfig` via a structured schema output—"SHALLOW" or "DEEP"—routing to the appropriate RAG operation.[2]
- **Conditional edges** in the graph enforce routing—only trigger deep, resource-intensive crawls when explicitly justified by intent.[2]
- **Shallow RAG node**: Fast, low-cost vector store retrieval; returns top K and synthesis.
- **Deep RAG node**: Multi-step web API fetch, crawl, synthesis—higher accuracy at cost/latency, used for complex, current, or comparative queries.
- Both paths merge at a synthesis node for subsequent tool orchestration.

## 6. Intent-Driven Dynamic Tool Management & Composability
- **IntentClassifierAgent**: Early node—analyzes message for domain and needed functionality. Curates required static/dynamic tools into execution graph. Conditional inclusion based on intent.[2][3]
- **Dynamic Tool Agent**: Assesses tool registry VDB (vector DB). Semantic similarity on existing tool schemas/descriptions:
  - **Use Existing**: High sim (>0.9), directly retrieve and use.
  - **Modify/Compose**: Moderate sim (0.6-0.9): chain/modify existing tools via LCEL (LangChain Expression Language).
  - **Create New**: Low sim (<0.6), generate new tool (code+schema with LLM), serialize LCEL sequence for registry/versioning.[2]
- All tools implemented as LCEL RunnableSequence objects, wrapped in `.as_tool()` with abstracted schema/name.[2]

## 7. Workflow Definitions
### 7.1 Chat Workflow
- RAG enrichment → DynamicToolGeneration → Agent (streaming onchatmodelstream) → ToolExecutorNode (parallel calls) → loop until response synthesis.[3]
### 7.2 Research Workflow
- QueryExpansion → Conditional search (deep/shallow) → SourceValidation → Synthesis → FactCheck. Intent-driven config (max_sources, retrieve_full_content); context enforced by StateManager.
### 7.3 Multi-Agent Workflow
- Supervisor → AgentNodes → Handoff via LangGraph Command(goto=agent_name) primitives, passing conversation/history context across agents.

## 8. Testing, Monitoring, and Error Handling
### 8.1 Rigorous Testing Requirements ([3])
- **Unit Tests**: For each node type, registry, and orchestration logic, with LLM-mock objects.
- **Integration Tests**: Full workflow end-to-end, including streaming output verification.
- **Performance Tests**: Test RAG workflow with different depths/max_sources for correct resource and context handling. Ensure workflow cache proper operation and system latency thresholds.

### 8.2 Monitoring and Observability
- **Metrics**: Dynamic tool generation count, streaming event latency, cache hit/miss, node execution time.
- **Logging**: Structured logs per workflow start, node executions, tool generations, and streaming chunk output.

### 8.3 Error Handling
- **Error Handler**: Node-level error counting and recovery with exponential backoff, retry logic, circuit-breaker configs, and error propagation in GraphState.[3]
- **CircuitBreakerProtection**: For all unstable/extensive-latency nodes to prevent cascading failures.

## 10. Success Criteria & Validation
- **Code Quality**: Cyclomatic complexity reduced 40%, clean separation of concerns, reliable error handling.
- **Performance**: Workflow cache hits <100ms, node execution <5ms overhead, memory reduction 20+%.
- **Maintainability**: New workflows in <1 hour, dynamic tools via registry w/out server changes, documentation for all primitives.
- **Reliability**: 99.9% uptime, graceful error degradation/recovery.
- **Backward Compatibility**: Feature flags, gradual rollout, legacy API support.
- **Risk Mitigation**: Profiling for performance regressions, anti-pattern documentation, regular arch reviews.
